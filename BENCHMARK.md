# RAG Head-to-Head Benchmark — rag-kit vs LlamaIndex

Measured comparison on the **same corpus, same questions, same LLM, same local
embedding model**. No LLM judges — correctness is exact phrase matching
against ground truth verified to exist in the corpus.

### Why the numbers look different from the earlier run

The first benchmark run (rag-kit 11.3s / LlamaIndex k=2 6.3s / k=10 70.1s)
was measured with the model's default **chain-of-thought leak**:
`qwen3.5-flash` emits a verbose "Thinking Process:" preamble inside the
answer text, which dominated latency and inflated output tokens for both
systems (rag-kit hit the 1,024-token output cap on 19/20 questions). The
current run disables reasoning on **both** sides with the same API parameter
(`reasoning: {"enabled": false}` — the setting a production RAG would use),
so the table above is the true pipeline-vs-pipeline comparison. Output
collapsed from ~1,024 to 74 tokens/query for rag-kit; latency from ~11s to
2.3s.

### How to read this

- **rag-kit wins accuracy at every configuration**: 95% vs 80% (k=2) and
  95% vs 90% (k=10), with the same retrieval hit rate as k=10.
- **At equal accuracy, rag-kit is faster than LlamaIndex's best config**:
  the terse pipeline answers 19/20 questions in 2.3–4.2s where k=10 takes
  5.2s for 18/20.
- **LlamaIndex k=2's speed is its accuracy loss** — 0.9s but 15 points
  behind, because 2 raw chunks produce thin answers (47 output tokens).
- **Context efficiency:** rag-kit feeds 10 trimmed/reranked chunks in fewer
  prompt tokens (1,669) than LlamaIndex needs for 2 raw chunks (1,941) —
  trimming + cross-encoder reranking do real work.
- **Cost parity:** $0.000128/query vs $0.000138 (k=2) / $0.000091 (k=10) —
  the quality difference comes from retrieval design, not from spending more.
- **Scoring honesty:** Q10 (`sqlite3.Error`) is missed by every system —
  the phrase requires module-qualified naming while all three answer
  "Error"; the question set accepts either phrasing of Q6 (`:name` or
  `colon`). Both are documented in `benchmark/questions.py`.
- Not measured here: multi-modal, 50+ data connectors, streaming, LangSmith
  observability, and community ecosystem, where the frameworks lead.

### Async vs sync (order-swap controlled)

rag-kit ships an async query path (`RAGSystem.aquery`) with shared keep-alive
HTTP clients (`httpx.Client` / `AsyncClient`). Measured with the same 20
questions, run order swapped to control for server warm-up:

| Order | First system | Second system |
|---|---|---|
| sync → async | sync 19.0s avg | async 8.8s avg |
| async → sync | async 12.7s avg | sync 10.5s avg |

*(Measured with reasoning enabled — the chain-of-thought leak inflated both
sides' absolute numbers; the relative conclusion is unaffected.)*

**Conclusion: no measurable single-query latency difference between async
and sync** — per-query latency is dominated by LLM generation, and the
"second system wins" pattern shows the gap is server-side variance, not the
async mechanism. Both paths score 19/20 accuracy. The async path's real
value is **concurrency** (serving many users without blocking worker
threads), which a sequential benchmark cannot measure — wire it into
FastAPI/Flask deployments for that benefit.

If per-query speed is the goal, the levers are output size (lower
`max_tokens`), model choice, or a terser synthesis prompt (`terse=True`) —
not sync/async.

## How it's measured (fairness contract)

| Dimension | Setting |
|---|---|
| Corpus | `benchmark/corpus/sqlite3.txt` — the CPython `sqlite3` documentation (RST source, identical bytes to both systems) |
| Questions | 20 factoid, ground-truth phrases verified present in the corpus (`benchmark/questions.py`) |
| LLM | `qwen/qwen3.5-flash-02-23` via OpenRouter, temperature 0.1 (same for both) |
| Reasoning | Disabled on both systems with the identical API parameter `reasoning: {"enabled": false}` (removes the model's chain-of-thought preamble) |
| Embeddings | `sentence-transformers/all-MiniLM-L6-v2`, local (same for both) |
| Scoring | Answer contains ground-truth phrase; retrieval hit = phrase present in the context the system actually fed the LLM |
| Cost | Measured API tokens × live OpenRouter price (fetched at run time) |

## Configurations compared

| System | Chunking | Retrieval | Context fed to LLM |
|---|---|---|---|
| rag-kit (terse) | 1200 chars, 200 overlap, heading-aware | FTS5 BM25 + rapidfuzz + local vector + FlashRank cross-encoder rerank, top-10, sentence-window trimming | TOC (up to 1k chars) + top-10 trimmed chunks + concise synthesis prompt |
| rag-kit (standard) | same | same | TOC + top-10 trimmed chunks + comprehensive synthesis prompt |
| LlamaIndex (default) | 1024 tokens, 20 overlap | Vector top-k=2 (library default) | top-2 nodes |
| LlamaIndex (k=10) | same | Vector top-k=10 | top-10 nodes |

rag-kit runs its default pipeline (`RAGSystem.query` / `RAGSystem.aquery`);
the terse variant is `rag.query(..., terse=True)` — a one-word API switch.
LlamaIndex runs its default query engine (`VectorStoreIndex.as_query_engine()`)
— the out-of-the-box experience.

## Re-running

```bash
cd benchmark
python3 -m venv .venv
.venv/bin/pip install -e .. "llama-index" "llama-index-readers-file" \
    "llama-index-embeddings-huggingface" "llama-index-llms-openrouter" \
    sentence-transformers
OPENROUTER_KEY=<your key> .venv/bin/python run_benchmark.py          # standard
OPENROUTER_KEY=<your key> .venv/bin/python run_benchmark.py --terse  # concise prompt
```

Output: markdown on stdout, machine-readable JSON in `results/latest.json`.

Use `--only ragkit` / `--only llamaindex` to run one side, `--corpus <path>` to
benchmark your own document, `--model <id>` to swap the LLM, `--async-first`
to check order effects, `--no-top-k-extra` to skip the k=10 run.

## Why these numbers matter

- **Answer accuracy** — end result quality, same LLM on both sides
- **Retrieval hit rate** — isolates retrieval quality from LLM quality
  (deterministic, zero LLM cost)
- **Latency** — end-to-end seconds per question
- **Tokens & cost** — prompt efficiency (rag-kit's trimming vs raw chunks)
